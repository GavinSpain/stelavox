## Project Overview

Stelavox is a hierarchical structured writing tool with AI agent assistance. Authors build a tree of nodes (Book → Act → Chapter → Scene → Beat) and AI agents operate at each layer to expand structure, synthesise prose, and refine content. The product is a web application built with Next.js 15, Supabase, and the Anthropic API.

## Architecture Rules

**LLM calls:** Never call the Anthropic SDK or Vercel AI SDK directly from a component or API route. Always use `getProvider()` from `lib/llm/factory.ts`.

**Operational values:** Never hardcode token budgets, prices, model IDs, durations, or limits in TypeScript. All operational values live in the `platform_config` database table and are read via `getConfig(key)` from `lib/config/platform-config.ts`. See Technical Architecture v1.5 §3.7 for the complete key registry.

**Token budget gate:** Always call `checkTokenBudget()` before creating an agent job record. The gate runs in the API route. If the budget check fails, no job record is created. See H-07.

**User content in prompts:** All user-authored content must be escaped with `escapeXml()` and wrapped in `<user_data>` XML tags before reaching any LLM prompt. See Technical Architecture §4.2.

**Canary token:** `injectCanary()` must be called on every system prompt. `scanForCanaryLeak()` must be called on every model response before use. See Technical Architecture §4.4.

**RLS:** API routes never filter by `user_id` directly. They rely on RLS at the database level. Always use the server Supabase client (not the anon client) in API routes.

**Migrations only:** Never modify the database via the Supabase Studio SQL editor. Write a numbered migration file. After every migration, regenerate types: `supabase gen types typescript --linked > lib/types/database.ts`. Never edit `lib/types/database.ts` by hand.

**Director write tools:** Write tools in the Director agentic loop produce `WorkflowStepProposal` objects — they never execute database writes inside the loop. Execution happens only after the author approves the plan. See H-08.

## The Six Inviolables

These cannot be overridden by any design decision. A violation is always wrong. (Was five; Inviolable #6 added at Phase 8.01 close-out, 2026-05-31.)

**1. Prose surface is lowest-noise surface.**
`ProseEditor` and `FocusMode` backgrounds are always `--color-bg-base` (#0d1014 dark / #f2ede4 light). Never lighter. Never elevated.

**2. Verdigris appears in exactly twelve places.**
`--color-accent` (#3d7858 dark / #254a38 light) appears only in:
1. Wordmark lozenge (`<Wordmark>`)
2. Wordmark rule (`<Wordmark>`)
3. Prose cursor (`<ProseEditor>` / `<FocusMode>`) — `caret-color: var(--color-accent)`
4. Agent-complete status badge (`<NodeStatusBadge>`)
5. Approved status badge (`<NodeStatusBadge>`)
6. Word count at target (`<WordCount>`)
7. **Affirmative-action triggers** — buttons and toggles that commit user-driven action against an agent or workflow proposal. Specifically:
   - Accept button background in Agent Tab (`<AgentTab>`)
   - Approve button background in PlanCard (`<PlanCard>`) — Component Spec v2.8 §1.4
   - Send button background in DirectorInput (`<DirectorInput>`) when the input has content — round-3 audit B-Inviol broadening 2026-05-10
   - Per-step approval checkbox border + background in PlanCard when checked (`<PlanCard>`) — round-3 audit B-Inviol broadening 2026-05-10
8. Primary plan CTA on trial expiry modal (`<TrialExpiryModal>`)
9. Active node left border in tree (`<NodeRow>`) — 2px left border
10. **Document-row ordinal tile** on the Project page Documents tab (`<ProjectDocumentsTab>`) — `--color-accent-muted` 36×36 tile background + `--color-accent-hover` numeric digit. Category: Catalog. Added 2026-06-03 by Brand Identity v2.3.
11. **Document-type identifier chip** — both the small stack-tag chip next to document-row titles in `<ProjectDocumentsTab>` and the larger stack-badge next to the project title in the Project page header (`<_ProjectPageClient>` Header). `--color-accent-hover` border + text. Category: Catalog. Added 2026-06-03 by Brand Identity v2.3.
12. **Document-row "Open" hover-action link** — the primary navigation affordance in the document-row hover-actions strip (`<ProjectDocumentsTab>`). `--color-accent-hover` text. Sole admitted hover-state verdigris use; admitted by exception under the Catalog category because entering a document is the singular primary verb against the Documents tab. Category: Catalog. Added 2026-06-03 by Brand Identity v2.3.

Search for `--color-accent`, `#3d7858`, and `#254a38` before any new use. Every match must be one of these twelve *categories*. Use #7 admits a family of "user-driven affirmative-action triggers" (Accept, Approve, Send, step toggle); use #11 admits both the small chip and the larger badge variant of the document-type identifier; uses #10 and #12 are single-element. New uses outside the catalogued twelve require an explicit Inviolable amendment (Brand Identity §5.3 three-test gate).

**3. Cinzel appears only in the wordmark.**
Only in `components/brand/Wordmark.tsx` and the S in `components/brand/AppIcon.tsx`. Never elsewhere.

**4. The typeface boundary is absolute (panel-vs-panel — original framing restored).**
`SummaryEditor` uses Inter only. `ProseEditor` uses Lora only. The Director conversation thread — both halves — stays Inter (Brand Identity v2.5, 2026-06-03: the v2.4 Lora-for-Director-bodies refinement was walked back after live review found the change confused the reading register; the agent's voice should read as system-level direction, not as in-progress prose). No Lora in any structural panel. The typeface transition is the mode signal: it fires at the prose editor boundary, nowhere else.

**5. The prose editor has no visible toolbar.**
Formatting via keyboard shortcuts and `SelectionTooltip` only (Bold · Italic · Link). No toolbar at rest. No heading controls. No visible formatting chrome.

**6. Cormorant Garamond italic appears only in the wordmark.**
Only in the *vox* component of `components/brand/Wordmark.tsx`. Never in the product UI, never in marketing copy, never as a heading typeface, never in body text, never decoratively. Symmetric protection alongside Inviolable #3 (Cinzel-only). Added at Phase 8.01 wireframe lock 2026-05-31 after Dashboard iter4 silently collapsed the mark to single-Cinzel "Stelavox" — the asymmetry had been a latent failure mode. Brand Identity v2.2 §3.2 + §6.1 + §12 are canonical.

## Known Hazards (summary)

Read Technical Architecture v1.9 §5 for the full entries (H-01 to H-15). H-16 through H-20 are introduced by Director V2 (TA v2.3 §A.4); full entries will be authored in a next TA revision. The most common during active build:

- **H-01** — Use `.maybeSingle()` not `.single()` when zero rows is a valid result
- **H-02** — RLS policies on `organisation_members` must not query `organisation_members`
- **H-03** — Organisation + membership creation must be a single atomic transaction
- **H-04** — Node reordering must update all affected siblings in one transaction
- **H-05** — Always clean up Supabase real-time subscriptions on component unmount
- **H-06** — Extract plain text from Tiptap JSON before including in any LLM prompt
- **H-07** — Token budget gate runs in the API route, before the agent job record is created
- **H-08** — Director write tools never execute inside the agentic loop
- **H-09** — BYOK API key retrieval only in Edge Function memory, never in API routes
- **H-10** — Regenerate `lib/types/database.ts` after every migration, never edit by hand
- **H-11** — Scheduler uses `FOR UPDATE SKIP LOCKED` to prevent duplicate job execution
- **H-12** — No hardcoded operational values in TypeScript — all values via `getConfig()`
- **H-13** — `SECURITY DEFINER` functions must declare `SET search_path = public`
- **H-14** — `documents ↔ layer_stacks` insert order: stack first (NULL doc_id), then document, then UPDATE
- **H-15** — Leaf-ness is a layer-stack property (`node.layer_index === max(layers[*].index)`), never inferred from child count — clients consume server-derived `is_leaf`
- **H-16** — Cascade rule completeness — server-derived cascade rules must cover all known dependency types; uncovered cascades produce silent context corruption
- **H-17** — Reservation TTL hygiene — throttle reservations without consumption-or-expiry produce phantom holds on capacity
- **H-18** — Brief preference type drift — `briefs.preferences` JSONB needs a lightly-typed validator at amendment-write time
- **H-19** — Stage trigger cycles — compound triggers can form cycles; cycle detection at brief-proposal validation
- **H-20** — Pricing rate effective_from race — stored `cost_credits` at call completion is the authoritative price; rate lookup is by call's completion date

**v1.43 — 2026-05-24** **M-210 — node_versions integrity: GUC-first trigger + skip-snapshot-on-expand + UNIQUE backstop.** Discovered via the v1.42 VersionHistory click-to-preview pane: clicking any version row produced "Could not load v{N}" because the `getVersion(node_id, version_number)` helper uses `.maybeSingle()`, which errors when multiple rows match the same `(node_id, version)` pair. Five nodes in the live DB had duplicate snapshot rows all numbered v=1 despite multiple agent Accepts. Live `nodes.prose` was always correct — only the history numbering was corrupted.

**Two root causes, both fixed in one migration:**

(1) **Trigger short-circuit on identical content.** The M-035 trigger `bump_node_version_on_content_change` required BOTH the session GUC `stelavox.bump_version='true'` AND a real content delta (`NEW.prose IS DISTINCT FROM OLD.prose` for any of summary/prose/notes/metadata) to bump `nodes.version`. When `accept_agent_job` applied content that happened to be byte-identical to what was already on the node — possible when an agent retry submits the same result, when a low-temperature synthesise re-runs deterministically, or when autosave wrote the same bytes between dispatch and accept — the trigger saw no diff and silently skipped the bump despite the caller's explicit GUC signal. The snapshot INSERT at the top of accept_agent_job ran unconditionally, so duplicate (node_id, version) snapshot rows accumulated. *Verified empirically*: a fresh accept_agent_job call with target_prose equal to current nodes.prose produced snapshot v=1 and left nodes.version=1.

(2) **Unconditional snapshot for expand.** `accept_agent_job` inserted a node_versions row for every accepted job — including `expand`, which per M-034 doesn't modify the parent's content fields. Repeated expand on the same parent produced multiple snapshots at the same version, all with byte-identical content (pre- and post-expand content matches because expand changes structure, not content). Node `8706dfed` in the live DB had four agent_expand snapshots all at v=1 for exactly this reason.

**M-210 contents (single migration, six steps in one transaction):**

(A) `SET LOCAL session_replication_role = replica` to bypass triggers during the backfill UPDATEs. (B) Renumber duplicate snapshot rows in-place: for each affected node, `ORDER BY created_at ASC` and assign `version = ROW_NUMBER()`. The oldest snapshot keeps its original v=1, subsequent rows take v=2, v=3, …. Snapshots are not FK targets, so renumbering is safe. No data lost. (C) Reconcile `nodes.version = MAX(node_versions.version) + 1` for every node that has snapshots — restores the "live points one past highest snapshot" invariant. Five duplicate-version groups renumbered; 68 nodes reconciled. (D) `ALTER TABLE node_versions ADD CONSTRAINT node_versions_node_id_version_unique UNIQUE (node_id, version)` — structural backstop. Future regression of either root cause now fails loudly with a constraint violation instead of silently corrupting history. (E) Rewrite `bump_node_version_on_content_change` to **GUC-first** logic: when `stelavox.bump_version='true'`, ALWAYS bump both `version` and `content_revision` regardless of content delta — the caller's intent is the bump signal, not the byte diff. Autosave path (GUC unset) preserves the existing "bump content_revision only on real content change" behaviour; TC-A-11 ("Same content does not bump version") still passes because that test doesn't set the GUC. (F) Rewrite `accept_agent_job` to skip the `INSERT INTO node_versions` when `operation_type='expand'`. Expand changes structure, not content; the snapshot would be redundant noise.

**Empirical verification:** a fresh accept with target_prose IDENTICAL to existing nodes.prose now bumps v=1 → v=2 (pre-M-210: stayed at v=1). A fresh accept with operation_type=expand creates zero snapshot rows (pre-M-210: created one at the unchanged version). **v1.40 — 2026-05-23** **M-205 — Apollo iteration-fork fix + state-machine CAS sweep.** User-driven testing of the v1.39 simplified Brief model surfaced an iteration-tree fork bug: brief `024da309` ("The Cavern Revealed") proposal turn produced 7 `director_iteration` agent_jobs in parallel branches where it should have produced 4 in a clean chain. The state machine had a hole, and the runner wasn't honouring its verdict.

**The Apollo fix is three concentric layers + one layer-0 foundation:**

1 migration (M-205, ~280 lines SQL) + 1 new shared helper (`lib/orchestration/cas-lookup.ts`) + edits across 5 entity machines + 4 API routes + iteration-runner + executor + dispatcher + simulator. Net +616 / -90 lines across 17 files.

**Layer 0 — TRUE CAS on `transitionAgentJob` (and all four other machines).** Surfaced by Simulator Scenario 11 (concurrent claim race): the DB's `enforce_legal_transition` trigger only raises when `OLD.state IS DISTINCT FROM NEW.state`. Setting `state=X` on a row already at `state=X` is a no-op UPDATE — trigger skips, UPDATE silently succeeds. Two concurrent `transitionAgentJob` callers both saw `ok=true` because the second's UPDATE was a same-state no-op. Fix: shared `casLookupSources(client, entityName, event, target)` helper queries `allowed_transitions` for the legal source state(s); every entity machine adds `.in('state', expectedSources)` to its UPDATE. Loser races match 0 rows and return `error='cas_lost'`. Applied uniformly across **agent-job-machine, brief-machine, brief-stage-machine, workflow-machine (transitionWorkflow + transitionWorkflowStep), director-turn-machine** — the entire orchestration library is now CAS-consistent. `TransitionResult.error` gains `'cas_lost'` and `'no_transition_for_event'` values.

**Layer 1 — Runner honours the CAS verdict.** `lib/director/iteration-runner.ts` claim block now reads `if (!claim.ok) { yield error; return }`. The losing runner yields a typed `claim_lost` event and exits silently. No LLM call, no spawn, no further writes. Six lines of code restore the contract: writers trust the state machine.

**Layer 2 — `consumer_kind` partition.** New `agent_jobs.consumer_kind TEXT NOT NULL DEFAULT 'dispatcher'` (CHECK in `{'inline_route','dispatcher'}`) partitions iteration rows by execution surface. `inline_route` = route handler at `/api/director/message` (or `/resume`) owns the row; `dispatcher` = scheduler owns (push-model planning, autonomous resumes). Two-sided gate: `agent_jobs_notify_insert` trigger fires `pg_notify` ONLY for `consumer_kind='dispatcher'` rows, AND `runDispatcherTick`'s candidate query adds `.eq('consumer_kind', 'dispatcher')` as defence-in-depth. Spawn-next trigger (Layer 3) propagates parent's `consumer_kind` to child INSERT. `startDirectorTurn` gains optional `consumerKind` parameter; both inline routes (`/api/director/message` + `/api/director/conversation/[id]/resume`) explicitly pass `'inline_route'`; the push-model evaluator (`evaluate_ready_stage_triggers`) omits and gets the safe `'dispatcher'` default. Dispatcher cannot see inline rows by any path.

**Layer 3 — Spawn-next is a state-machine action.** New `agent_jobs.stop_reason TEXT NULL` is stamped by the runner on the `running → awaiting_accept` transition. New `trg_agent_jobs_spawn_next_iteration` AFTER UPDATE trigger fires when `stop_reason='tool_use'` and INSERTs the next iteration atomically inside the same transition transaction. The 40-line INSERT block in `iteration-runner.ts` is deleted; the runner SELECTs the trigger-spawned child by `parent_iteration_id` to populate `next_iteration_job_id`. Two partial unique indices enforce chain shape structurally: `agent_jobs_parent_iteration_unique` on `(parent_iteration_id) WHERE parent_iteration_id IS NOT NULL` (every parent has at most one child); `agent_jobs_turn_iteration_unique` on `(director_turn_id, iteration_number) WHERE operation_type='director_iteration'` (no two iterations share a number within a turn).

**State-aware `markAgentJobCancelledAnyState` helper.** Multiple API routes (`/api/scheduler/jobs/[id]/cancel`, `/api/agent-jobs/[id]/cancel`) used `cancel_or_cascade` as their cancel event regardless of row state. Pre-CAS this silently succeeded because the (from, to) pair was legal via a different event (`cancel_mid_dispatch`, `cancel_mid_run`). Post-CAS the lookup returned only `['queued']` and the UPDATE failed for any other active state. New `markAgentJobCancelledAnyState(client, jobId, reason)` reads the row's current state, dispatches to the correct event-state pairing, returns idempotent success on already-terminal rows. Both cancel routes migrated.

For each fork: earliest-started child per parent is preserved as canonical chain owner; later children + ALL descendants get `parent_iteration_id=NULL` and `iteration_number=NULL`. **The architectural principle this change makes structural:** writers don't decide consequences.
