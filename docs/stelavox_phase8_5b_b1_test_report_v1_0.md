## 1. What shipped

### 1.1 Migration `M-212` — `20260608000212_document_and_project_rollup_rpcs.sql`

Two new Postgres RPCs:

- **`get_document_rollup(p_document_id UUID)`** — returns one row of aggregates per document. Replaces the TS-side row-sum that previously hit PostgREST's 1000-row response cap.
- **`get_project_rollup(p_project_id UUID)`** — returns one row of aggregates per project, summing across its documents.

Both `LANGUAGE sql STABLE` with `SECURITY INVOKER` + `SET search_path = public`:
- **SECURITY INVOKER** (NOT DEFINER) so RLS on the underlying `nodes` query scopes the aggregate to what the caller is authorised to see (TC-8.5b-B1-06 verified this — anon cross-org call returns zero, not the real data)
- **search_path = public** per H-13 (search-path injection hardening is independent of RLS mode)

One new index: `idx_nodes_document_id_layer_index` on `nodes(document_id, layer_index) WHERE node_category = 'structural'` — accelerates the `MAX(layer_index)` subquery used to derive leafness inside the RPCs.

### 1.2 New TS files

- **`lib/types/api.ts`** — single source of truth for the new API response shapes (`DocumentRollup`, `ProjectRollup`, `StructuralNodeRow`, `FullNodeRow`, `NodeIncludeField`, `STRUCTURAL_COLUMNS`, `ALLOWED_INCLUDES`). Tier-A §2.5 contract.
- **`lib/queries/rollups.ts`** — typed thin wrappers `getDocumentRollup(supabase, docId)` and `getProjectRollup(supabase, projId)`. Wraps the RPC calls with COALESCE-style empty-result handling (zero-filled, never null).
- **`app/api/documents/[documentId]/rollup/route.ts`** — GET endpoint returning `DocumentRollup`.
- **`app/api/projects/[projectId]/rollup/route.ts`** — GET endpoint returning `ProjectRollup`.

### 1.3 Modified TS files

- **`lib/dashboard/projectAggregates.ts`** — public function signature `getProjectAggregates(supabase, orgId)` unchanged. Internal rewrite drops the 2-query / TS-sum implementation; replaces with `projects.query + N parallel rollup RPCs`. Old TS-sum code path deleted entirely.
- **`lib/project/getStructuralOverview.ts`** — `computeChildActualAggregates` paginates its `nodes` fetch via `.range(...)` loop. Per-subtree rollup semantics preserved (this helper needs per-immediate-child sums, not document-level totals, so it doesn't switch to the RPC). 1000-row cap risk eliminated.
- **`lib/types/database.ts`** — regenerated by `supabase gen types`. RPCs surface as typed `.rpc('get_document_rollup', ...)` and `.rpc('get_project_rollup', ...)`.

### 1.4 Test files

- **`tests/unit/rollup-rpcs.test.ts`** — NEW. 11 cases (TC-8.5b-B1-01..10 + TC-8.5b-B1-15 pagination probe). Run against real fixtures (Sample Novel, Shadow Protocol, Mega Manuscript).
- **`tests/v1x-phase8-5b/dashboard-mega-doc.spec.ts`** — NEW. 4 Playwright cases (TC-8.5b-B1-11..14) verifying the dashboard ProjectCard renders the rollup values end-to-end.
- **`tests/unit/structure-overview-data-path.test.ts`** — MODIFIED. Mock chain gains `.range()` no-op pass-through so the pagination loop in `computeChildActualAggregates` doesn't fail with `range is not a function`. 10/10 cases still pass.
- **`tests/unit/project-aggregates-data-path.test.ts`** — SUPERSEDED. Replaced by a stub with a supersession note. The original tests pinned the `.eq('is_leaf', true)` anti-pattern, which is structurally impossible under the new RPC-based shape. Replacement coverage lives in `rollup-rpcs.test.ts` + `dashboard-mega-doc.spec.ts`.

### 2.4 Mid-test correction logged

**TC-8.5b-B1-06 initially failed** when first run because the migration declared `SECURITY DEFINER`. SECURITY DEFINER bypasses RLS by default (function runs with owner privileges). The intent was for the RPC to respect the caller's RLS scope, so anon cross-org callers would see zero.

**Fix applied:** changed both RPCs to `SECURITY INVOKER` in the migration file + applied the updated SQL via `docker exec ... psql` (since the migration tracking entry was already in place, can't re-run `supabase migration up`). The Tier-A spec §4.1 stated the intended behaviour ("anon callers RLS-scoped"); the migration body initially didn't match. Now consistent.

The migration file lands at v1.1 of this commit with the corrected mode. Documented inline at §4.1 of the spec and at the migration's header comment.
