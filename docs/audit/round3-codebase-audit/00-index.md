# Round-3 codebase audit — index

**Started:** 2026-05-10
**Method:** for each function: form independent hypothesis from signature/name/file context BEFORE reading comment or code; then compare hypothesis vs stated (comment) vs actual (code) vs spec.

## Methodology

For each function:

1. Read signature only. Write down a hypothesis: "what should this do, given its name + signature + the subsystem it lives in + how the file describes itself?"
2. Read the comment/JSDoc. Compare to hypothesis.
3. Read the code. Compare to hypothesis AND comment.
4. Skim 2–3 call sites. Does caller usage match the hypothesis?

Any divergence is catalogued.

## Severity

- **HIGH** — silent semantic bug (wrong behaviour on hot path; comment claims X but code does Y; callers depend on behaviour the function doesn't deliver). Production-impacting.
- **MEDIUM** — code matches comments but contradicts what callers need; or comment is misleading enough to cause future bugs; non-hot-path silent issues.
- **LOW** — vague/wrong/missing comments, dead code, premature abstraction, naming. Worth fixing but not bug-shaped.

## Categories

- `comment-vs-code-mismatch` — comment claims one thing, code does another
- `silent-failure` — code can fail/return wrong thing without throwing or logging
- `wrong-semantics` — code does something, but the wrong thing for what callers need
- `dead-code` — function/branch unreachable or always-false
- `callers-disagree` — callers use the function in a way inconsistent with what it actually does
- `spec-drift` — code drifted from a spec it was originally written against
- `spec-divergence` — code+comment+intent all agree, but the spec (docs/) says something different. The spec is authoritative per global CLAUDE.md, so this is still a finding.

## Confidence

- `certain` — I can point to the exact line that's wrong; the divergence is unambiguous
- `likely` — the divergence is real but I want a second pair of eyes
- `worth-checking` — something feels off; may be intentional but documenting in case
