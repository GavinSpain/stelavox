§ 1 · INTRO + LOCKED DECISIONS
Single admin page at /admin/payments sibling to the V1.x-E /admin dashboard. Same env-var auth (PLATFORM_ADMIN_EMAILS); Inter-only typography; no verdigris (admin surfaces don't host author-facing affirmative-action). 5 tabs, all server-rendered with TanStack Query for the live counters.

The page is the single source of truth + control surface for every payment-system parameter, every observation surface, every failure path. Every config-key write is audit_log + cache-invalidate.
Page shape
Single route with 5 internal tabs (Configuration · Price IDs · Health · Events · Failures). Tabs persist via ?tab= query param so admin can bookmark a specific surface.
Write access
In-app forms for every Stripe config key. Each write triggers audit_log insert with {key, old_value, new_value, admin_user_id} + _clearConfigCache() so changes reflect immediately.
Auth
PLATFORM_ADMIN_EMAILS env-var allowlist (matches V1.x-E). Non-admin → redirect to /dashboard. Service-role client for all reads + writes.
Past-due gate (NEW lock)
Paid plans with subscription_status='past_due': immediate Director/agent cutoff. Full app + writing access preserved during Stripe's Smart Retries window (~14 days). If retries exhaust → subscription.deleted → trial revert → trial-expiry redirect.
Refunds + disputes (NEW lock)
Add charge.refunded + charge.dispute.created + invoice.payment_action_required to HANDLED_EVENT_TYPES. Light handlers; no auto-action; full surface in admin Failures tab with Stripe Dashboard deep-link.
Multi-currency
USD-only V1 (matches Stripe Prices created at $20/50/120/15 USD baseline). Read-only "Current currency: USD" display on Configuration tab with "Multi-currency support — V2" note. Prices have currency baked in; multi-currency = matrix of Price IDs.
§ 2 · TAB 1 — CONFIGURATION
Every Stripe + billing config key, grouped by concern. Read-only fields are env-var or display-only; all editable fields write via Server Action → UPDATE platform_config → audit_log insert → _clearConfigCache(). The save button per row activates only when the value diverges from the current DB value; on success it flashes "Saved" inline for 2s, then disappears.

§ 8 · NUMBERED CALLOUTS
1Mode swap — `stripe.mode` flip is instant; the validator re-runs on next API call to check the new mode's keys are populated. If they aren't, Checkout returns 503 with explicit `missing` list (existing behaviour).
2API version extraction — removes the only hardcoded payment parameter in the codebase. M-223 adds the config key with the current `'2026-05-27.dahlia'` as default; `lib/stripe/client.ts` reads it at client construction. Drift-guard test forbids `apiVersion:` literals.
3Checkout option keys — three new keys (automatic_tax_enabled, allow_promotion_codes, billing_address_collection) read by `createCheckoutSession`. Defaults preserve current behaviour. Validator extends to require these alongside the existing 12 (mode + 8 Price IDs + webhook secret + api_version + 3 new = 13 active checks).
4Currency display — explicit read-only field with V1=USD lock and "Multi-currency support — V2" note. Prevents the silent assumption that "we support whatever Stripe supports".
5Grace gate semantics — `billing.payment_failure_grace_days` becomes live. Past-due gate cuts LLM immediately but preserves app access for N days. After N days the org gets the trial-expiry-style hard cutoff (not implemented in V1 wireframe; ship the soft cutoff first, hard cutoff is V1.x).
6Validate-against-Stripe — admin action that hits Stripe's `prices.retrieve` for every non-empty Price ID and reports back: product name + recurring interval + amount + currency. Catches typos + cadence mismatches at admin-config time, BEFORE the user fails Checkout. Implementation: server action calling `stripe.prices.retrieve()` per ID with timeout.
7Past-due list ordering — by last-failure-time ASC (longest in past_due at top). Stripe Smart Retries typically span ~14 days; orgs at the top are closest to forced cancellation.
8Webhook ingestion lag — `NOW() - max(subscription_events.created_at)`. Healthy threshold < 60s. Spikes indicate Vercel cold starts, Stripe outages, or webhook-handler bugs.
9Dispute card — `--error` border + critical severity. Pre-formatted to the standard Stripe dispute timeline (admin has ~14 days to respond with evidence). Surfaces the response deadline explicitly.
10Refund card — `--review` border (high but not critical). Refunds are admin-initiated; this is observational, not actionable.
11Past-due banner copy — emphasises "your work is safe" (matches the writing-never-blocks ethos) and "7 days" (matches `billing.payment_failure_grace_days`). The dynamic value reads from config so changing the grace updates the copy.
§ 9 · OPEN DECISIONS
D1 · Webhook secret edit flow The wireframe shows the secret as a password field with a "Reveal" + "Edit" button. Should editing require re-confirmation (type the new secret twice, or require typing the current secret first)?
D1.a Type new twice — standard pattern
D1.b Type current secret to unlock edit — higher friction, fewer accidents
D1.c No re-confirmation — trust the admin allowlist
Recommend D1.a
D2 · Trial duration change retroactivity Current copy reads "Existing trials are NOT retroactively changed". Should there be a "Recompute existing trials" admin action that resets `trial_expires_at = signup_at + NEW_duration` for all current trials?
D2.a Never retroactive — minimum surprise
D2.b Admin action with confirmation — flexible but dangerous
Recommend D2.a (and document the action exists as V1.x escape hatch)
D3 · MRR calculation source Tab 3 shows an "MRR · estimated" card. Calculate from our DB (count active subs × plan price) or via Stripe API call (canonical but rate-limit-sensitive)?
D3.a DB calculation — fast, no Stripe call; estimate may drift from Stripe's view by < 1%
D3.b Stripe API call cached 5min — canonical but adds API dependency
Recommend D3.a with explicit "estimated" label + Stripe deep-link
D4 · Past-due gate enforcement layer The user said "LLM access cuts immediately". Implement at: (a) credit gate `checkTokenBudget` — same layer as today; (b) `(app)/layout.tsx` — early return like trial-expiry; (c) both?
D4.a Credit gate only — Director route refuses; user sees the existing 402 error
D4.b Layout — full app rendered but Director button disabled across all surfaces
D4.c Both — defence in depth + clearer UX
Recommend D4.c
D5 · Refund/dispute audit_log severity Wireframe shows dispute = `critical`, refund = `high`. Confirm or adjust.
D5.a As shown
D5.b Both critical — disputes AND refunds need attention
Recommend D5.a (refund was admin-initiated; not surprising)
D6 · Notify trial-ending users Tab 3 shows "Notify all" on the trials-expiring list. Send what — Stripe trial-ending email (built-in), our own email, both?
D6.a Rely on Stripe's `customer.subscription.trial_will_end` automated email (3 days before)
D6.b Custom email through our own provider (V1.x — needs email infrastructure not yet shipped)
D6.c Defer the Notify button entirely from V1 wireframe
Recommend D6.a now + D6.c hide the button (Stripe handles it)
