Project page · Documents view
1
Sidebar project sub-nav. When you're inside a project, the sidebar's project section becomes the navigation: Documents · Profile · Activity · Export. Plus the Context library always lives below. Mode tabs at the top (Edit / Director / Focus) are disabled at the project level — they activate when you've opened a specific document. Honest UX: the modes apply to a document, not a project.
2
Stack badge near project title. Series of Novels in monospace verdigris. Tells you the layer_stack at a glance. For a Novel project it'd read "Novel"; for Anthology it'd read "Anthology"; etc. Single source of truth for "what shape of work is this project."
3
Document rows. Each = one document. Numbered (1, 2, 3) for position within the project. Title + small "Series · 3 books" tag (telling you what the document's tree contains at the top level of its layer_stack). Meta line tucks last-edit + node count + status events. Progress bar column standardised — same shape as the tree's word-count column from Edit Mode iter3. Hover reveals quick actions: Open · Export · Archive.
4
Project Profile card. Compact summary of voice / tense / locked decisions / named-entity counts. "Edit →" link to the full Profile tab. The profile is project-level — shared across all 3 documents in this project. This makes the "shared context across the catalog" benefit explicit.
5
Recent activity panel. Lightweight feed of recent agent operations across all documents in the project. Acts as a "what happened while I was away" surface. Click → Activity tab for the full feed.

Project page · Export
1
Tree-with-checkboxes scope picker. Same bracketed-label vocabulary as Edit Mode iter3 — [Series 1], [Book 1], [Act 1], etc. The project's documents sit at the root level; their internal trees expand below. You can check any node at any layer — the output is determined by what's selected.
2
Partial-fill checkbox. When some-but-not-all descendants are checked, the parent shows a "−" partial-fill indicator (rather than full check or empty). Standard pattern — but worth calling out because it makes the export scope unambiguous: "this series is partly selected; click to expand and see which books are included."
3
Auto-selection rules. Checking a parent selects all its descendants. Unchecking a descendant makes the parent partial. Independent across documents — you can export Book 1 of Foundation + Book 3 of Robot Series in one go. One mental model: "tick what you want."
4
Format picker — 2×2 tile grid. EPUB / DOCX / PDF / Outline. Verdigris-active on the selected format. Each tile shows the format name + a one-line descriptor. Tiles instead of dropdown because format choice is meaningful and worth showing the options without a click.
5
Output summary in plain English. Tells you exactly what will come out: "1 file: Foundation.epub · 76,000 words · 4 acts · 30 chapters · 142 beats." Updates live as the selection changes. For multi-doc selections the summary becomes "2 files: Foundation.epub + Foundation-and-Empire.epub · …" or "1 bundle (foundation-trilogy.zip)" depending on the user's bundle preference (open for iter2 — see decisions).
03 — Writer's eye · iter1
A writer with three series — the project page is "where do I want to write today?"

I'm imagining I'm working on three connected series (Asimov-style) — they share characters, a unifying galactic history, named locations. The project page is the surface where I see all of that together. I'm not writing here. I'm deciding what to do, or seeing what was done while I was away, or pulling everything together for export.

What works in iter1

The Documents list is what I'd want. Each row tells me the doc's state at a glance — progress, last edit, what the Director's been up to, whether anything needs my review. The hover-revealed actions mean I don't need to click in to do something common. The Project Profile card on the right is a quiet "you're at the project level now" signal — it shows the shared voice / decisions / named entities. That's the reminder that this is where the cross-series consistency lives.

The Export tree-with-checkboxes is the right model. "Tick what you want." Same vocabulary as the rest of the app (bracketed labels), same visual rhythm, same hierarchy. The output preview answers the only question I have when exporting: "what will I get?" Plain English. No surprises.

What I'd push or revise
P-1
The mode tabs at the top are disabled at the project level. That's correct (modes apply to a document, not a project), but having them visible-but-disabled is visual noise on a project page. Three options: (a) hide them entirely, (b) replace them with "← Project" breadcrumb-style chip, (c) keep them disabled with a tooltip "Open a document to use Edit / Director / Focus." I'd hide them — the user understands modes once they're in a document.
P-2
Single-document projects (most standalone novel users). Right now the wireframe shows the multi-doc case. For a standalone novel (1 project, 1 document), the project page is mostly redundant — the writer wants to be in Edit Mode, not staring at a single-row list. Options: (a) clicking the project from Dashboard auto-opens the doc's Edit Mode and the Project page becomes accessible only via sidebar; (b) Project page still appears but collapsed to "Open document →" + Profile + Context shortcuts. Recommend (a). Project page is for the multi-doc case; single-doc users skip it.
P-3
"Documents" tab title is correct but feels generic. For Series-of-Novels projects, the docs are series. For Anthology projects, they're anthologies. For Novel projects, they're books. Worth pulling the label from the layer_stack's top-level node_type plural — "Series", "Books", "Anthologies", "Papers". Costs nothing once Phase 14 lands; for V1 we hardcode the two cases.
P-4
Bundle vs separate files. When the user selects multiple documents for export, the output is "N files." But the user might want them bundled (one .zip / one bound .epub). Need a toggle: "Output as: ● Separate files · ○ Single bundle." Could live alongside the Format picker. Iter2 candidate.
P-5
Profile card is a summary, not editable inline. "Edit →" sends you to the full Profile tab. That's right — the profile is dense and deserves its own surface — but the summary card itself could show one more thing: a small "Last updated 3 days ago" timestamp. So the writer knows whether the profile reflects current state.
P-6
Activity panel is too compact for "what changed while I was away." Three rows is enough for "right now" but not for "I haven't logged in for 3 days." Either (a) expand the side card to show 5-7 rows when there's substantial activity, or (b) auto-route to the full Activity tab on first visit when there's >N unread events. I lean (b) with a subtle "5 new events since you were last here" header in the Activity card.
P-7
Export — "Export →" is a big verdigris button. Big-button-end-of-flow is correct. But for novice users the lack of confirmation might be scary. Should there be a "Preview first?" link beneath the Export button that opens a quick render preview (especially for EPUB)? Probably not for V1 — adds complexity. Flag for V2.
P-8
"+ New document" is a primary action when the layer_stack permits multiple documents. What about layer_stacks that imply single-document (e.g., a hypothetical "Single Novel" layer_stack that's strictly one book per project)? The button needs to be hidden in those cases. For V1 both Novel + Series-of-Novels allow multiple documents in principle, so the button stays. Worth thinking about per-stack constraints in Phase 14.
Honest gut feel

The two-column layout (docs on the left, profile + activity on the right) reads as "where I am, what's here, what happened." That's the right job for a project page. Export is the most polished part of the wireframe — the tree-with-checkboxes maps cleanly onto user intent ("tick what you want"). The main thing I'd want to address next is P-2 — making sure single-document users don't see this page unnecessarily — and P-3 — using the layer_stack's terminology consistently. Both are small iterations.
