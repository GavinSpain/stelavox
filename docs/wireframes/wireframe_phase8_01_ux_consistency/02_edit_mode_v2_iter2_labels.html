02 — Notes & decisions
Why I recommend Option A

Brackets are the disambiguator. Look at the bottom "edge case" rows. In Option A the row reads [Act 1] Act 1 — the system-generated label is visibly distinct from the author's name, even when they happen to share the same string. In Option B the same row reads Act 1 Act 1 with no visual separation; the two collide.

Monospace anchors the metadata. JetBrains Mono / ui-monospace at 10.5px in the bracketed label feels like a structural tag. Inter at the same level (Option B) is harder to distinguish from the name's typography at small sizes. The eye learns "this looks like metadata" within seconds.

Tabular alignment is automatic. Mono fonts have a fixed column width, so labels at the same indent level naturally align vertically — [Book 1] / [Book 2] / [Book 3] line up perfectly down the page. With Option B's proportional Inter the alignment drifts.

Subtle layer-tinting preserved but no longer load-bearing. Both options use a faint per-layer colour on the label only — for those who notice it, it's a secondary cue. The label text itself is the primary identifier. No more "what colour is sea-glass vs slate."

Series-aware hierarchy
Document shapeLayer stack (top → bottom)
Standalone novelBook → Act → Chapter → Scene → Beat
Trilogy / seriesSeries → Book → Act → Chapter → Scene → Beat
Long series (Reacher-style)Series → Book (1..N) → Act → Chapter → Scene → Beat
Anthology, paper, etc.(future) — different stacks per layer_stacks

No special-casing for any layer. The labelling logic is the same at every level: type-name + position-within-parent. The system reads nodes.order for the position. No UI-side counting; no drift.

Director reference vocabulary (locks in for 8.03)

The unambiguous Director-side reference becomes a structured path of layer + position pairs. Examples:

What the writer types in @-pickResolves to
@act1ch2sc3bt1Act 1 → Chapter 2 → Scene 3 → Beat 1
@b2act1ch2Book 2 → Act 1 → Chapter 2 (series context)
@ch2 (when in scope of one Act)Disambiguates from a single ancestor
@ + node nameFree-text picker — falls back to existing name search

This eliminates the name-matching ambiguity we hit with "The Countdown" earlier (three nodes with the same name across two scenes and one beat). Out of scope for 8.01 visual pass — Director tool work is 8.03 or later. Locking the direction now so the visual labels and the future tool surface share one vocabulary.

Abbreviation question — still open

Current draft uses Book / Act / Ch / Sc / Bt. Book and Act stay full-word (short enough). Chapter / Scene / Beat abbreviate (long words at deep indents would crowd the name column). Series gets its own word.

Alternative: every layer abbreviates (B / A / C / S / Bt) — most compact, but Book / Act lose their immediately-readable form. Or every layer full-word (Book / Act / Chapter / Scene / Beat) — most readable, but at indent level 5 the labels eat ~80px of name column.

Recommend the current mixed form — readability where it costs nothing, abbreviation only at deeper indents. Your call.

Data migration concern (for the eventual functional ship)

Existing Shadow Protocol data has nodes named Act One: The Salvage, Act Two: The Bonding etc. — the author manually prepended structural labels because the system didn't show them. Once the new label system ships, the redundant prefix should be stripped. Two options for the migration:

(a) Automatic clean-up on the system-prefix pattern (^(Act|Book|Chapter|Scene|Beat) (One|Two|\d+):\s*) → strip and bump updated_at. Reversible.

(b) Show a one-time banner per document offering the user to "Clean up structural prefixes from node names — these are now auto-displayed."

I'd recommend (b) — the author keeps control, and they explicitly choose to migrate (or not). Tracked as an 8.03 functional task.
