Two shapes, one template
1
Shared header. Both panes carry the bracketed label + title + meta-line. Same visual rhythm. The eye knows it's looking at the same kind of object regardless of layer.
2
Non-leaf = "see the structure." Summary + Author's note + Aggregate metrics + Children list with mini-progress bars + Recent activity scoped to subtree. The dominant block is "In this Act · 2 chapters" — what's beneath, at a glance.
3
Leaf = "read & write the prose." Summary stays compact at the top (the author's reminder of what this beat is for). The dominant block is the prose canvas in Lora 16px — same typography as Focus Mode. A subtle verdigris caret marks the cursor position. Word-count meter docked at the bottom. The eye doesn't see the chrome; it sees the words.
4
Different tabs per shape. Non-leaf: Overview · Notes · Activity · Comments · History. Leaf: Content · Notes · Activity · Comments · History. The first tab swaps because the "default" view is fundamentally different — structure overview vs prose content.
5
Different actions per shape. Non-leaf actions: + Expand (primary, verdigris) / Refine summary / Generate context / Lock. Leaf actions: Refine (primary) / Synthesise / Comment / Lock. Same docked-bottom bar; contextually appropriate verbs.
6
"Open in tree →" link on the children block. Quick affordance for the writer who wants to drill into a child without going back to the tree pane. Same pattern for "Open in Focus Mode →" on the prose block.

03 — Writer's eye · the detail pane in practice
Two days of writing — what each detail pane actually does

I notice my own use of detail panes is bimodal. When I'm structuring (planning the next act, deciding where the next chapter break goes, checking my progress) I want to see the shape of the work below the row I clicked. When I'm writing (open a beat, type) I want everything else to disappear — just the prose and the word count. The non-leaf vs leaf split mirrors those two modes directly. That's why this iteration feels more honest than the iter1 attempt where every detail pane had the same Summary / Prose / Notes shape regardless of node type.

What works

The "In this Act · 2 chapters" block does the work of "where are we." I see Ch 1 (complete) and Ch 2 (3 running) and the eye finds Ch 2 immediately — that's where the active work is. I can act from this view without going back to the tree — click Ch 2's row and the detail pane updates. One-level navigation inside the detail pane reduces tree-pane traffic significantly.

The aggregate metrics row (Chapters / Scenes / Beats / Running / Review) is a clean five-cell summary. Numbers in JetBrains Mono so they have weight and rhythm. 3 running in blue jumps off the page when I'm scanning for what to attend to next.

The Beat detail pane is the cleanest the prose-writing surface has ever been. The Summary stays present (one tap of attention) but the dominant block is the Lora prose canvas. The verdigris caret indicator at the end of the last paragraph is the kind of detail that says "this is a writing tool, not an editor for someone else's text."

What I'd push or revise
D-1
The "Aggregate" block reads as analytics-dashboard rather than writing-tool. Five numbers in mono is information-dense but emotionally cold. Counter-proposal: collapse to a single narrative line — "This Act contains 2 chapters, 3 scenes, 11 beats. 3 beats are running, 1 needs review." Inter 12px, italic for the numbers. Same info, warmer register. Worth trying in iter2.
D-2
The Beat detail pane shows the cursor at the end of the last paragraph. What if I want to edit a sentence in the middle? The mock shows only end-of-doc caret. In a real editor the caret follows clicks. The wireframe should hint at click-to-edit by showing a brief hover state on a mid-doc word. Minor visual — not a real concern.
D-3
Same width for both pane shapes. Currently both are 480px. The non-leaf overview pane feels right at 480; the leaf prose pane might want to be wider (560-620px) so the prose has room to breathe. Two options: variable pane width per shape, or both stay 480 and we trust the writer to use Focus Mode for full immersion. I lean the latter — Focus Mode is the answer to "I want to disappear into the prose," not "make the right panel wider."
D-4
"Open in Focus Mode →" link on the prose block. That's the right escape hatch but it should probably be a keyboard shortcut too (⌘.). Showing keyboard shortcuts inline on hoverable affordances might be a separate consistency pass (one of the items on the original Phase 8 list — global keyboard shortcuts).
D-5
The Activity block scoped-to-this-subtree is a real win. When I click an Act and see "the last 3 things that happened anywhere under this Act," I get exactly the information I want without scope-creeping into other Acts. Worth ensuring scoping is consistent everywhere — a Chapter's Activity block shows ops in that Chapter only; a Book's shows the whole book; etc.
D-6
"+ Expand" as the primary action on non-leaf panes assumes the most common next action is "have the Director propose children." That's true at planning time. At polishing time the most common action is "refine summary." Counter-proposal: primary action adapts based on the node's state — if the children block has no children (un-expanded), primary is + Expand. If children exist but the summary is short, primary is Refine summary. If everything's filled in, primary is + Expand (a new sibling). Small heuristic, big UX win.
D-7
Notes tab. Both panes have a Notes tab but the content is invisible in the mock. In the implementation Notes is the author's private scratchpad (Inter 13px, sibling to Summary). Worth showing in iter2 — a peek at what Notes looks like, because it's the surface where the author talks to themselves between Director conversations.
Honest gut feel

This is the closest the detail pane has come to feeling like a craft tool instead of a structural editor. The non-leaf shape gives the writer enough state without forcing them back to the tree pane every time. The leaf shape — Summary + prose canvas + word meter + minimal chrome — is what the writing surface should always have been. D-1 (warmer aggregate block) and D-6 (state-aware primary action) are the two refinements I'd want to see in iter2. Beyond that, this lands.

04 — Decisions iter1
Locked in this iteration
Two pane shapes
Non-leaf (Book / Act / Chapter / Scene) and Leaf (Beat). One template per shape; same chrome (header / tabs / actions) so they read as the same kind of object.
Shared header
Bracketed label + title + meta-line. Bracket colour matches the layer tint (same as tree).
Non-leaf tabs
Overview · Notes · Activity · Comments · History. Overview = default.
Leaf tabs
Content · Notes · Activity · Comments · History. Content = default.
Non-leaf body
Summary card · Author's note · Aggregate metrics · Children list · Recent activity (scoped to subtree).
Leaf body
Summary card · Prose canvas (Lora 16px, caret animation) · Word-count meter docked at body bottom.
Children list
Compact rows with bracketed label · name · mini progress bar · lifecycle pill. Click → detail pane updates to that child. "Open in tree →" link to return to the full tree pane.
Action bar
Docked bottom of pane. Non-leaf: + Expand (primary) · Refine summary · Generate context · Lock. Leaf: Refine (primary) · Synthesise · Comment · Lock.
Activity scoping
Recent activity in detail pane is scoped to the subtree of the current node. A Chapter's activity = ops on its scenes + beats only. A Book's = all ops in the book.

D-5 activity scoping
