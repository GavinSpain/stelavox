Layout decisions implied here.
  • Three-pane layout collapses to two below 1280px; tree is the first thing to become slide-over below 1024px.
  • Director Mode never collapses below the panel + tree split — at iPad portrait the tree slides over the conversation, not the other way around. The conversation is the user's task surface; tree is a navigation aid.
  • Slide-overs are always edge-anchored: tree from left, director from right, focus is its own full-screen Portal.
  • Touch targets: every tappable element has a 44px minimum hit area. The summon buttons, tree rows, tab buttons, Esc button — all meet HIG.

08 — Writer's eye review

What worked. The slide-over pattern keeps the iPad design honest with the desktop one — no app reflow, no different component shapes, just panes moving from pinned to slide-over by breakpoint. The bracketed-label vocabulary travels well to small widths because the labels are inherently compact. Detail-pane structure-overview for non-leaf nodes (Section 05 detail pane) works the same on iPad as on desktop — the previously-decided shape was viewport-agnostic.

What I'd watch.

  • I-1 — Detail pane prose column cap. At iPad landscape (760px detail pane), uncapped prose runs to ~660px. The desktop reads at 640–680px line-width. Confirming the same ~640px max-width cap applies on iPad — content centres in the remaining space.
  • I-2 — Director Mode portrait layout. Not shown above — should detail collapse and Director go full-width, or detail-as-summary-strip-on-top + Director full-width below? Recommend the second (a 100px summary strip showing the current node), so the conversation always has context without a tree open.
  • I-3 — Swipe gesture interference with text selection. Standard iPad text selection uses long-press to begin selection. Our beat-nav swipe uses horizontal swipe. These shouldn't conflict, but worth a tactile test in build. If interference shows up, the fallback is two-finger horizontal swipe for beat-nav.
  • I-4 — Long-press timings (350ms drag, 800ms context menu). Slightly tweakable. The 350ms drag-start delay needs to feel decisive without false-positives during scroll. iOS standard is 500ms for drag, 1000ms for context — we're tighter on both. Worth a tactile pass in build.
  • I-5 — Status pip touch targets. The 6px status dot in tree rows is decorative-only — not tappable. Tap anywhere on the row selects. Confirming this matches Phase 6 lock UI expectations (status pip is informational, not interactive).
  • I-6 — Slide-over width. Tree slide-over at 320px. Some content (long node names with bracketed labels) will still truncate. Acceptable — long names truncate everywhere; the bracketed position is what matters.
  • I-7 — Portrait Director Mode. Worth a dedicated section in iter2 if I-2 needs more visual debate.
  • I-8 — Phone layout. Out of scope for V1. Document as Backlog row in the phase plan — phone is V2 polish at minimum.

09 — Decisions

Locked (no further iter needed unless you object)

  • ● Breakpoint rules. ≥1280 three-pane · 1024–1279 two-pane · 768–1023 single-pane with slide-overs · <768 out of V1 scope.
  • ● Tree summon icon ☰ in header, 44px hit, mode-independent.
  • ● Slide-over edges. Tree from left, Director from right, Focus is full-screen Portal.
  • ● Tree slide-over width 320px (wider than landscape's pinned 260px because tap targets need breathing room).
  • ● Tree row min-height 44px across all viewports (was 36px on desktop in Component Spec §4.2; the new 44px holds on both iPad and desktop — desktop loses no functional density, gains tap-friendliness).
  • ● Tap on bracketed crumb label navigates up. Universal in detail header and Director context strip.
  • ● Swipe gestures in Focus Mode mirror ⌘ ← / ⌘ → desktop behaviour from wireframe 06.
  • ● Five Inviolables. Unchanged. Verdigris-use count remains nine.

Open — need your call

  • ● I-1 — Prose column cap on iPad. Recommend keeping the desktop ~640px max-width cap inside the detail pane (centred in the available width). Approve, or let prose fill the pane?
  • ● I-2 — Director Mode portrait layout. Recommend 100px summary strip on top + Director full-width below. Approve as the portrait shape, or full-width Director with tree summon only?
  • ● I-4 — Long-press timings. Recommend 350ms for drag, 800ms for context menu. Approve, or use iOS standard (500/1000)?

Deferred (Phase 8.x sub-items or Backlog)

  • ● I-3 — swipe vs text-selection tactile interference test (build-time verification, not wireframe).
  • ● I-7 — dedicated iPad-portrait Director Mode wireframe (only if I-2 needs visual debate).
  • ● I-8 — phone layout, V2+.
