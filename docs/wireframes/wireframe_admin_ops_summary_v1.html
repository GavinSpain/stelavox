DR-121 expanded · Admin Operations Summary · v1.0 · 2026-06-14
What this covers. The new Operations Summary that leads /admin — five bands answering “is the whole system healthy right now,” above the existing per-subsystem sections. Folds in the six cross-cutting gaps: health rollup, liveness/heartbeats, external dependencies, volume/growth, export/storage, plus the original DR-121 scheduler-calibration surfaces. Tiles carry a status dot — green / amber / red. Inter only; no verdigris — status-green is --color-success, a distinct token from brand --color-accent.

Annotations · metric source derive = SELECT only · capture = small new write
1Overall health pill.derive One of Healthy / Degraded / Critical, computed from capacity alerts + probe outcomes + heartbeat staleness. Critical needs a core-dependency-down or critical alert; high alerts / stale transport = Degraded. The sub-line reassures that author writing is never affected by ops state.
2Active issues.derive The deduplicated list behind the pill — each row is severity + one line + a deep-link to the section that explains it. Empty list ⇒ “All systems nominal” on a green pill.
3Heartbeat tiles. Dispatcher derive (last tick age); cloud transport derive from net._http_response — the prod failure most likely to be silent; realtime capture (new round-trip probe); pg_cron derive from cron.job_run_details. Green < fresh · amber < stale · red ≥ dead.
4pg_cron expand. Per-job rows for the 5 scheduled jobs — last-run age + ✓/✗. This is the authoritative “are my background jobs alive” source.
5Dependencies. Anthropic derive from the existing director_small probe + agent-job error rate; DB derive via SELECT 1 latency; Stripe derive from last-webhook age + ingestion lag. All three are the things whose silent failure breaks the product.
6Volume & growth.derive Orgs by plan/status, new + active orgs, trial→paid conversions — all SELECTs over organisations + agent_jobs + subscription_events. Sparklines over the window selector (1h/24h/7d).
7Activity trends.derive Tokens/day, Director turns/day, agent jobs/day. Gives the “is usage growing” signal the point-in-time payments counts lack.
8Export volume.derive Counts by format + outcome, failed-export rate — newly relevant after the DR-042 per-book rework.
9Storage.capture Needs export_jobs.file_size_bytes (runner computes byte length at upload — persist it). Shown against the per-file limit raised in the DR-042 discussion.
10Subscriber mix.derive Plan × status × cadence. Counts from organisations; monthly/yearly split from stripe_price_id → priceIdToPlan().cadence. byok_solo is flagged — it pays a flat fee and carries no token budget.
11Token economics by cohort.derive The headline table — Trial included. Per cohort: users · tokens · real Cost $ (SUM agent_jobs.cost_usd) · budget-util bar with calendar-elapsed pace marker · Revenue · Net. Past the marker ⇒ on track to exceed budget (Author, proj ~136%). Pro at 24% reads as over-allocated. Totals footer. byok_solo excluded (no platform tokens / budget).
12Trial liability.derive Broken out because trial tokens are pure cost, no offsetting revenue. Trial cost this period + projected month-end + avg cost/trial + cost per converted trial (÷ Band-4 conversions) — the acquisition-spend read. Converting ⇒ investment; leaking ⇒ tighten the trial grant.
13Platform spend by model.derive SUM(agent_jobs.cost_usd) WHERE route='platform' GROUP BY model_id — this is the Anthropic invoice, per-model, cache-tier aware. Actual tokens + actual $, already captured per job. Reconcile directly against the Anthropic dashboard.
14Run-rate + MoM + tier check.derive Projected month-end $ (consumed ÷ elapsed fraction); month-on-month platform $ trend for capacity planning; a plain-language note on which Anthropic tier the current usage fits.
15BYOK comparison — informational only.derive route='byok' rows: count + avg tokens/user vs platform. Surfaces that uncapped BYOK users burn ~2.6× — useful for budget + fee sizing. $0 to the platform; never used for internal billing.
Decisions — locked 2026-06-14 (wireframe Bands 1–7 approved)
OA-1 · Placement. Operations Summary renders as bands atop the existing /admin; not a separate route.
OA-2 · Endpoint. New /api/admin/ops — keeps the existing dashboard payload stable; ops reads independently cacheable.
OA-3 · Realtime probe cadence. Every 5 min — realtime failures are rare; a per-minute sentinel write adds noise.
