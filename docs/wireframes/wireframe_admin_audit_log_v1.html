Context

DR-096 lands audit_log writes on every critical event (security frame violations, H-08 breaches, workflow-advance failures, job-transition failures, job failures, usage-record write failures). The author's requirement: "I want to be able to see this in the admin section." This wireframe adds a seventh section to the existing /admin dashboard — below Synthetic Probes — following the established fetch + render pattern (one new keyed field on the GET /api/admin/dashboard payload).

Decisions Locked (proposed)
D1 — Section, not page. The viewer is a section inside the existing AdminDashboard, not a separate route. One payload field (audit_log_recent), one render block. The admin allowlist auth is inherited.
D2 — Window-selector aware. Rows respect the page-level 1h / 24h / 7d window like every other section. Default fetch: most recent 50 rows within the window; "Load more" fetches the next 50.
D3 — Severity filter chips. All · Critical · High · Medium · Info. Client-side filter over the fetched rows (the fetch always brings all severities so counts stay honest).
D4 — Click to expand. A row click expands the full metadata JSONB inline (monospace, pretty-printed) plus the soft-ref UUIDs (document / conversation / node). No modal.
D5 — No verdigris. Severity colours: critical = --color-error, high = --color-status-review, medium = amber family, info = --color-info. Admin surfaces add zero verdigris uses (consistent with V1.x-E).
D6 — Read-only. No acknowledge / dismiss / delete actions in V1. The audit log is an append-only forensic record; admin workflow actions are V1.x if a need emerges.
Stage — the new section in place

Annotations
1
Section header carries the window + count. "Audit Log (24h · 14 events)" — count is the unfiltered total within the window, so the admin can see volume at a glance even with a severity chip active.
2
Severity chips with counts. Client-side filter; counts always reflect the fetched window. Active chip = --color-bg-surface + border-strong. Dot colours per D5 — zero verdigris.
3
Five-column row. Severity (dot + label) · relative time · event_type (monospace) with a one-line metadata preview underneath · org (short-UUID + name) · soft-ref hints (node / job / conversation when those UUIDs are present). Row height ~38px collapsed.
4
Expanded row. Click toggles an inline expansion: full pretty-printed metadata JSONB + absolute timestamp + full UUIDs. Monospace 10.5px on --color-bg-deep. No modal, no navigation — forensics happen in place. Click again to collapse.
5
Load more. Fetches the next 50 via ?audit_before=<created_at cursor>. Ghost button, neutral tokens. The dashboard's 30s poll refreshes only the FIRST page (newest rows); loaded history below stays stable so reading isn't disrupted.
Inviolable Audit

#2 Verdigris: zero uses added. Severity colours are error / status-review / amber / info families; chips and buttons are neutral. Count stays at twelve.

#3 Cinzel / #6 Cormorant: not present — admin chrome is Inter throughout, matching the existing dashboard.

#4 Typeface boundary: Inter + JetBrains Mono (established admin-surface convention for identifiers); no Lora.

#1 / #5: not in scope (no prose surface).

Open Decisions for review

OQ-1 · Poll vs realtime. The dashboard polls every 30s. Critical audit events (canary leak) arguably justify a realtime subscription so they appear instantly. Recommendation: stay with the 30s poll for V1 — audit_log isn't in the realtime publication, the admin is one person, and DR-019 (push notifications) is the V1.x answer for instant alerting.

OQ-2 · Cross-org visibility. The viewer shows ALL orgs (platform-operator view, service-role read like the rest of the dashboard). Per-org filtering ships when there are enough orgs to need it (a search box is a V1.x add). Recommendation: ship without org filter.

OQ-3 · Retention surfacing. audit_log currently has no purge job (rows accumulate). Fine for V1 volume; a retention policy joins the Phase 11 ops hardening conversation. Recommendation: note it in Phase 11's scope, nothing in this UI.
