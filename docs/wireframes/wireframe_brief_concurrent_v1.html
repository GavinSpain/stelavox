04 — Annotations
1
BriefViewer · existing mount, V1.x-D extension
Component Spec §17.2 baseline (V1.x-A.1) · §17.2 extension (V1.x-D)
BriefViewer has shipped since V1.x-A.1 as a read-only project-header surface for the active Brief. V1.x-D extends it for the multi-Brief world that V1.x-B.3 made possible: a switcher pill in the header and a concurrent-Brief indicator. The card content itself (goal + stages) is unchanged from the V1.x-A.1 baseline.
2
Brief switcher · pip-style multi-Brief selector
Component Spec §17.2 extension · V1.x-B.3 carry-over
Compact pill in the header. When only one Brief exists, shows Single Brief in muted text (no interaction). When multiple Briefs are active, shows Brief N of M with one pip per Brief; the active pip is filled, others empty. Click ▾ to dropdown a list with each Brief's title + status. The dropdown swaps which Brief the BriefViewer renders; the URL doesn't change (the page is still the same document).
3
Concurrent-Brief indicator · informational only
Component Spec §17.2 extension · V1.x-B.3 carry-over
Renders only when 2+ active Briefs exist on the document. Left border --info (neutral teal — same token as AI-changed flag and Stop honesty block; consistent "informational, not alarm" cue). Names the other Brief(s), summarises its stage, links to scheduler. No verdigris. Not interactive itself (read-only); links inside route the user to the scheduler or the alternate Brief view.
4
SchedulerPanel · multi-active extension
Component Spec §17.4 baseline (V1.x-B.1.1) · §17.4 extension (V1.x-D)
SchedulerPanel has shipped since V1.x-B.1.1 with single-active-Brief assumption (the V1.x-B.1.1 era had the strict-one-active partial unique index). V1.x-B.3 dropped that constraint; V1.x-D's extension is the multi-row "Active Briefs · N" group plus per-row indicators + actions. Each row is a Brief, not a workflow step (a Brief contains many workflows; expanding a row drills into its stages).
5
Per-row actions on active Briefs
Component Spec §17.4 · existing per-row Cancel + Open from B.1.1
Each active Brief row shows Open + Cancel. Open routes to the BriefViewer focused on that Brief (the dropdown switcher's target). Cancel uses destructive token + cascade-confirmation modal (existing V1.x-B.1.1 pattern, unchanged). Queued Briefs additionally get Reorder ↑↓ for queue-priority changes — existing affordance unchanged.
6
BriefProposalCard · existing affordance, new warning
Component Spec §A.7 (PlanCard family) · V1.x-B.3 detectConcurrentEditWarning lib call
BriefProposalCard renders inline in the DirectorPanel conversation thread when the Director proposes a Brief. The card itself (title + goal + stages + Approve / Reject) is unchanged. V1.x-D extension is the warning block that renders ONLY when the proposal's target_node_ids overlap nodes currently in another active Brief's running or planned stage. The data source for the warning is the V1.x-B.3 detectConcurrentEditWarning(documentId, proposedTargetNodeIds) helper which already exists.
7
Concurrent-edit warning block
Component Spec §A.7 extension · V1.x-D
Attention-amber left border + light amber background. Lists the overlapping nodes by name and the active Brief + Stage each is currently part of. Recommendation line names two paths (wait / cancel the other Brief). The Approve button copy changes from "Approve" to "Approve anyway" when the warning is shown — explicit acknowledgement that the user is opting into a potentially conflicting state. Approve button remains verdigris use #7 — affirmative-action triggers family, unchanged.
8
No-overlap variant · clean card
Component Spec §A.7
When the proposal targets nodes that don't overlap any active Brief, no warning block renders. Approve button reads the normal "Approve". This is the most common path — V1.x-D's warning is a guardrail for the cases where concurrent Briefs would step on each other, not a routine surface.
05 — Inviolable audit & open decisions
Inviolable #2 audit · no new verdigris

All three V1.x-D extensions reuse existing tokens. Concurrent-Brief indicator: --info (same as Stop refinement honesty block + AI-changed flag — informational neutral). SchedulerPanel multi-active rows: --ag-run active pulse + neutral row background. BriefProposalCard concurrent-edit-warning: --st-rev attention-amber (existing in-review status token). Approve button: --verd existing use #7. Verdigris-use count remains nine.

Open decisions before build
  1. Brief switcher placement. Drawn top-right of BriefViewer header. Alternative: a horizontal tab strip above the Brief title showing all active Briefs as tabs. Recommendation: keep the pill + dropdown — tabs would steal vertical space and most documents will have ≤2 active Briefs, so a full tab strip is overkill.
  2. Concurrent-Brief indicator visibility threshold. Drawn as "renders when 2+ active Briefs exist". Alternative: only when the OTHER Brief currently has a running step (filter by activity). Recommendation: keep the simpler rule — any 2+ active Briefs trigger the indicator; explaining "Brief is currently idle" adds confusion.
  3. "Approve anyway" copy. Drawn as a label swap when the warning shows. Alternative: keep "Approve" with a small modal confirmation when the warning is present. Recommendation: label swap is more honest at the affordance level; modal adds friction without adding clarity.
  4. Queued Brief auto-promote behaviour. Currently a queued Brief promotes when the first active Brief completes (V1.x-B.3 dropped the auto-promote behaviour; queue position is informational). Open: should the scheduler also surface "promote now" as an explicit user action on queued rows? Recommendation: defer to V2 — V1's queue model is "first-come first-served, manual reorder only". Auto-promote-now adds a path that can collide with the multi-active world.
  5. Cascade-confirmation copy on Cancel of an active Brief with concurrent siblings. Existing V1.x-B.1.1 cascade copy mentions pending stages cancelled / completed retained. Open: should it also mention "the sibling Brief X continues unaffected"? Recommendation: yes — explicit reassurance helps when the author worries that cancelling one Brief might break another. One-line addition to the existing copy.
