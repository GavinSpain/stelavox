05 — Annotations
1
Acknowledgement line — new message variant
Component Spec §17.11 · Director Arch v2.3 §10 closure principle
New conversation-message variant fired automatically when a workflow's terminal state is reached. Renders in-thread (not floating) so the conversation history reflects the closure. Left border --verd (2px) for success; --st-rev for partial; --destr for full failure. Verdigris border on success uses the existing #4 agent-complete category — a passive completion indicator, not affirmative action. Verdigris-use count remains nine.
2
PlanCard persists in complete state
Component Spec §7.6 (PlanCard baseline) · §17.7 extensions · §17.11 · simplified 2026-05-17
Pre-V1.x-D the PlanCard could fade or collapse on completion in some surfaces. V1.x-D locks the behaviour: the card persists in the conversation thread, marked complete, with every step visible. The author can see what ran and which steps succeeded. Per-step token costs are NOT shown (stripped 2026-05-17 across PlanCards in execution + completion surfaces) — consumption detail lives in CostMeter alone; per-step labels were audit data not author-decision data and added visual noise. The PlanCard's existing Approve button (verdigris use #7) is no longer relevant in complete state (workflow already approved + executed); it hides.
3
Partial-completion variant
Component Spec §17.11 · Director Arch v2.3 §10 five-class failure taxonomy
When some steps failed mid-workflow, the acknowledgement uses --st-rev attention-amber border + a half-filled glyph (◐). Copy declares the split ("6 of 8 succeeded") and surfaces a Retry affordance for just the failed steps (the existing per-step retry pattern; not invented here). Failure reason (e.g. output_schema_invalid = Class D) shown inline on the failed PlanCard steps in --destr text.
4
Full-failure variant
Component Spec §17.11 · Director Arch v2.3 §10
When zero steps succeed, border + glyph escalate to --destr. Copy names the failure class in plain English ("Rate limit hit on your provider · Class A — retryable") so the author understands whether to wait + retry or whether the failure is permanent. Class taxonomy: A transient (retry) / B interrupted (resume) / C capacity (back off) / D validation (intervention needed) / E hard system (support). The acknowledgement copy adapts per class.
5
Brief Stage completion variant
Component Spec §17.11 · Director Arch v2.3 §4.2 Stage triggers
Brief-driven workflows fire stage-completion acknowledgements when a whole Stage's workflows complete (not just one workflow). Copy mentions Stage progress + Brief name + offers a cross-link to BriefViewer for context. Important for multi-stage Briefs where the Director plans + runs sequential workflows without further user approval (V1.x-B.2.3 auto-approve subsequent stages). The author may not be watching — these acknowledgements are the surface that says "here's where we are".
6
V1 = mechanical only
Component Spec §17.11 · explicit V2 deferral
V1.x-D ships only the mechanical acknowledgement: counts, status, navigation. No commentary on output quality, no judgement, no proactive suggestions. This is deliberate — closes the "silent completion" gap identified in the Director V2 deep-dive without overshooting into chatty territory. The Director already says enough during the turn; the closing line should be quiet and informational.
7
V2 candidate · reflective acknowledgement
Director Arch v2.3 §16.3 V2 backlog
V2 candidate: Director re-reads its own artefacts at workflow close and surfaces an observation ("I notice Scene 4's tension arc is flatter than the others"). Adds an extra LLM round-trip + judgement complexity + token cost. Defer until user-driven testing confirms this is useful and not annoying. Today's V1.x-D mechanical line is the floor; reflective is an opt-in V2 enhancement.
06 — Inviolable audit & open decisions
Inviolable #2 audit · acknowledgement uses existing verdigris category

The acknowledgement line's left border on success uses --verd (2px) — this falls under the existing Inviolable #2 use #4 family (agent-complete status indicator). It's a passive completion declaration, not affirmative action. No new use category introduced. Verdigris-use count remains nine.

Partial border = --st-rev. Failure border = --destr. Both are existing tokens used elsewhere; neither is a new verdigris use.

Open decisions before build
  1. Acknowledgement copy length. Drawn as ~1 sentence. Open: should it be a single short line ("12 of 12 steps succeeded.") or include the navigation hint ("Review the changes in the tree…")? Recommendation: include the navigation hint when scenes are pending review; omit when nothing needs author action.
  2. Token / credit cost in acknowledgement. SETTLED 2026-05-17 — dropped everywhere outside CostMeter. Acknowledgement shows outcome counts only (N of M succeeded); per-step token labels also stripped from PlanCards in this wireframe. CostMeter remains the single dedicated surface for consumption detail.
  3. Class-specific copy for failures. Different failure classes need different copy (Class A retry-soon vs Class D author-intervention). Drawn for Classes A + D. Open: lock the exact copy per class now, or iterate during build. Recommendation: lock during build with a simple lookup table; this wireframe locks the shape, not the wording.
  4. Stage-completion acknowledgement frequency. Should every workflow-complete inside a Stage fire its own acknowledgement, plus a stage-complete acknowledgement on the last one? Drawn with the stage-complete only firing on the Stage's last workflow. Recommendation: yes — per-workflow acknowledgements would spam the thread on multi-workflow Stages.
  5. Cross-link target for failures. Drawn as "Retry the 2 failures →". Open: link to the failed agent_jobs view, or trigger a one-click retry inline? Recommendation: link first (lets author inspect the failure reason) — inline retry is a V2 polish.
