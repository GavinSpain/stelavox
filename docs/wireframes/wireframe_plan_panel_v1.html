03 — Annotations
1
Mount + page shell
Component Spec §1.x · matches /settings/api-keys + /settings/usage shell
Routes at /settings/plan. Same shell as the other Settings pages: max-width 720px, centred, ← Settings back-link, Inter 22px/500 h1. Settings index (V1.x-B.1.2 row) gains a fourth row "Plan" pointing here. The page is read-only in V1; V2 lights up Stripe Checkout for paid-tier changes and Vault upload for BYOK enable.
2
Current-plan banner
Product Spec v1.11 §3.1 · GET /api/usage/current-period (V1.x-C.4)
Sits at the top of the page as the unambiguous "what plan am I on" surface. Pulls plan slug, monthly/annual prices, allocation, and next reset date from platform_config (plan keys) + the org row's current_period_start. Realtime-subscribed to the organisations row so a plan change (V2) reflects immediately. Border uses --border-str to distinguish from the comparison tier cards below.
3
Platform tiers list
Product Spec v1.9 §3.1 Platform Tiers · seeded in platform_config v1.x-C.2 M-134
Four rows: Trial, Writer, Author, Pro. Prices read from price..monthly_cents and converted client-side; allocations from plan._token_allocation_credits. Current-plan row gets a verdigris dot + "Current plan" marker (use #4 family — "agent-complete / approved" status indicator; passive status, not affirmative action) and elevated background --hover. Other rows are neutral. Sort order matches pricing ladder.
4
BYOK tiers list
Product Spec v1.9 §3.1 BYOK Tiers · BYOK-eligible plans locked V1.x-C.3
Two rows: BYOK Solo, BYOK Team. The descriptions note multi-provider potential ("Anthropic or other provider") in line with the provider-neutral stance locked in CostMeter (no dollar surfacing). "Eligibility" is the V1.x-C.3 rule: only orgs on byok_solo / byok_team can upload a key via the M-137 RPCs. The PlanPanel doesn't enforce switching — switching happens through Stripe in V2 — but it shows the price and capability so the user knows what to ask for.
5
Switching-plans CTA — read-only in V1
Inviolable #2 use #8 reserved for TrialExpiryModal · this is informational, not the upgrade trigger
Dashed-border informational block; explicitly NOT verdigris. The "contact support" affordance is plain text — V1 has no in-app billing operations. Open decision: whether to include a mailto: or a support-portal link here. Recommendation: bare "contact support" copy in V1 with the email visible elsewhere in the app (existing support flow); a CTA link is misleading without a working portal.
6
Trial-expiry note (Trial variant)
Product Spec v1.9 §3.1 Trial · 30-day window
Trial users see a soft note below the current-plan banner counting down to expiry. This is informational — the formal trial-expiry experience is the existing TrialExpiryModal which fires on day 30 (Inviolable #2 use #8 lives there with its verdigris primary CTA). This PlanPanel note is dashed-border + muted; not a CTA, just countdown awareness.
7
BYOK user · status + Usage cross-link
Component Spec §17.6 (CostMeter) cross-link
BYOK users get one extra line under the current-plan price: provider-key status + a cross-link to /settings/usage (CostMeter full form, tokens-only). This is the navigational continuation between "what plan am I on" and "what have I used". No dollar amount surfaced here — provider-neutral as locked elsewhere. Key-status line mirrors the OrgAnthropicKeyPanel status pattern.
04 — Settled & open decisions
Settled (these flow from earlier decisions)
  • V1 is read-only. No Stripe / no in-app plan switching. Stripe arrives in V2 per Product Spec v1.9 §3.4.
  • Plan slugs are the locked Product Spec v1.9 §3.1 list: trial / writer / author / pro (Platform) + byok_solo / byok_team (BYOK). The build-checklist's earlier proposed enum (starter/pro/enterprise) is not used; CostMeter wireframe annotation already records this.
  • BYOK-eligible plans are byok_solo + byok_team only (V1.x-C.3 decision). PlanPanel reflects this in the BYOK section; the OrgAnthropicKeyPanel admin surface is the operational counterpart.
  • "View plans →" link from CostMeter routes here (per V1.x-D CostMeter open-decision resolution).
Open decisions before build
  1. "Contact support" affordance. Bare copy vs mailto: vs link to support portal. Recommendation: bare copy in V1 (no working portal yet); revisit when Stripe + support flows land.
  2. Trial-expiry note thresholds. Always-visible to trial users, or only when ≤7 days remaining? Recommendation: always-visible — trial users benefit from countdown awareness throughout; reduces day-30 surprise.
  3. Yearly price toggle. Wireframe shows monthly + annual on the same line. Alternative: a toggle pill that switches the entire grid between monthly and annual displays. Recommendation: inline display (current draft) — keeps the surface simple; toggle adds an interaction with no V1 commit path behind it.
  4. Trial-only orgs viewing BYOK rows. Should the BYOK section be hidden until the user is on a paid plan? Recommendation: keep visible — informational transparency about the full pricing menu. Trial users want to know their options.
