Annotations
1 CapabilityLimitCard. Renders in conversation thread when an iteration emits capability_limit_artefact. Left border is --color-info (not --color-error) — this is the Director recognising its own limits, not a failure. Header pill icon is the warning glyph in --color-info.
2 Suggested alternative block. The model's structured proposal of what it can do — surfaced separately from the reason text so the user can act on it without re-reading the explanation. Background --color-bg-elevated + 2px left accent in --color-info.
3 "Adjust request" link. Text-link with subtle bottom border in --color-border-strong — informational affordance, not verdigris (there is no approval; the user reformulates their request manually). No button background; no fill.
4 Class A toast. --color-info left border. Surfaces only at 2nd retry onward — first retry stays silent (most transient errors resolve invisibly). Auto-dismisses after 6s. Message body shows attempt counter so the user knows how close we are to giving up.
5 Class C toast. --color-status-review left border (attention without alarm — same family as in-review status pill). Surfaces when a job is paused by the WFQ dispatcher's back-off. Auto-dismisses after 8s (slightly longer than Class A — capacity events are rarer and the user benefits from a moment to register them).
6 Class D banner. 3px left border in --color-error. Remediation block in the elevated surface tone tells the user what to do, not just what happened. Action link opens the affected node — no automatic retry (validation failures usually need user intervention).
7 Class E banner. Full border in --color-error plus a low-saturation red gradient background — visually heavier than Class D because Class E is exceptional and worth pausing for. Tone is collaborative ("the team has been notified") not blame.
8 Contact support CTA. mailto: link populated with the job id pre-filled in the subject. Border in --color-error echoes the banner border. No system-prompt or stack-trace dump in the email body (privacy + the user shouldn't paste arbitrary content unknowingly).
Open decisions to lock before F.1 build
D1 · Class A first-retry silence. Should the Class A toast appear on the first retry or only on the second? Recommendation: silent on first retry; surface on second. Most transient errors resolve invisibly on retry 1; surfacing every transient blip becomes noise. Second-retry surfacing gives the user warning before the (final) third attempt.
D2 · Class C back-off threshold. Should every WFQ throttle event surface a Class C toast, or only when back-off duration exceeds N seconds? Recommendation: surface only when back-off ≥ 15s. Sub-second pauses are dispatcher-internal and shouldn't generate noise. Configurable via new failure.class_c_min_pause_seconds platform_config key (default 15).
D3 · Class E admin contact mechanism. mailto: link to a configurable address, or a dedicated in-app feedback form? Recommendation: mailto: for V1. Email address lives in failure.class_e_admin_contact platform_config key (default support@stelavox.io). In-app feedback form is V2 (requires a feedback table + admin inbox UI).
D4 · Dismissed-banner persistence. Should Class D / Class E banner dismissals persist across reloads (per-job-id in localStorage) or clear on reload? Recommendation: persist via localStorage failure-banner-dismissed:<job_id>. Same pattern as V1.x-D StoppedFollowOnBanner — keyed by job_id so each failure has its own dismiss state.
D5 · CapabilityLimitCard re-trigger. If the user re-sends the same over-capability request, does the Director re-emit the artefact or recognise it from conversation context? Recommendation: re-emit each time. Conversation rolling window may have dropped the prior artefact; re-emission is cheap and keeps the surface deterministic. Director prompt v1.10 doesn't add a "don't repeat capability_limit" instruction.
