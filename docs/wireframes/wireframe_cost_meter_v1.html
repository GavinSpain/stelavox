04 — Annotations
1
Compact form lives in AppShellStatusIndicator
Component Spec §17.1 · §17.6 · V1.x-B.1.1 shipped the AppShellStatusIndicator shell
The compact form is the rightmost segment in the existing AppShellStatusIndicator (bottom-right of the app, mounted in V1.x-B.1.1). V1.x-D lights up the cost segment — the surrounding Director-state badge and scheduler-counters are unchanged. No verdigris on this surface. The dot before "Director idle" uses --verd-h as a passive status colour from B.1.1 convention, not a new use.
2
Non-BYOK compact display
Component Spec §17.6 · Product Spec v1.9 §3.1 Platform Tiers
Pattern: NN% · renews in Nd. Percentage is token_usage_credits / token_allocation_credits from the org row. Days-remaining computed from current_period_start + plan.period_length_days. Click routes to the full form at /settings/usage. Realtime-subscribed to the organisations row's usage_credits column (incremented by M-135 trigger). No tokens, no dollars — non-BYOK users see only the simple "% of plan" + countdown.
3
BYOK compact display — tokens only, no dollar surfacing
Component Spec §17.6 · simplified per user direction 2026-05-17 · provider-neutral
Pattern: NNk in · MMk out. Token totals are this-period sums from agent_jobs.tokens_input and tokens_output filtered to the org. Dollar cost is deliberately not surfaced — three reasons. (1) Billing is between the user and their LLM provider; Stelavox is not the merchant of record on BYOK. (2) Cost calculations rely on time-versioned price tables (anthropic_pricing) that can drift from the provider's actual invoice; surfacing a wrong number is worse than surfacing none. (3) Future-proof for multi-provider BYOK (OpenAI / Google / Mistral per existing byok_provider CHECK constraint) where computing a unified dollar value across providers gets brittle. Tokens are provider-neutral and sufficient signal for the user to govern their own consumption. Numbers abbreviated to k (×1000) below 1M to stay compact; full digits at >1M.
4
Approaching-limit colour transition
Component Spec §17.1 alert-dot + §17.6 + Inviolable #2
At 80% usage the percentage number switches to --st-rev (attention-amber, same token the AppShellStatusIndicator already uses for its alert dot). At 100% the colour escalates to --destr (destructive red) and the alert dot's background follows. Director state shifts from "idle" to "paused" because the admission gate (V1.x-C.2 checkTokenBudget) starts refusing dispatch; the queued counter rises as queued items can't drain. No verdigris at any usage level — usage state is passive observation, not affirmative action.
5
Full form page shell
Component Spec §1.x layout shells + existing /settings/api-keys precedent
Mounts at /settings/usage. Reuses the existing settings page shell: max-width 720px, centred, ← Settings back-link at top, Inter 22px/500 h1. Same shell as /settings/api-keys (V1.x-B.1.2) and /settings/org-api-keys (V1.x-C.4). The Settings index (V1.x-B.1.2) gains a third row "Usage & Billing" pointing here.
6
Primary card — plan + usage (single card, no extras)
Component Spec §17.6 full form · API: GET /api/usage/current-period (V1.x-C.4)
One GET /api/usage/current-period?org_id=X populates the entire card: plan label, days-remaining, usage_credits, allocation_credits. Usage bar fills proportionally; same colour transitions as the compact form (0–80% neutral, 80–100% amber, 100% destructive). Realtime-subscribed to the organisations row. The denominator is the org's token_allocation_credits column (set by M-134 backfill and M-140 auto-allocation trigger on new orgs). Per user direction 2026-05-17: no per-project breakdown, no past-periods card, no history — keep it focused on "% of plan used" + "when does it reset".
7
Soft upgrade CTA — informational only in V1
Inviolable #2 use #8 belongs to TrialExpiryModal · routine top-up is neutral
The CTA uses a dashed border + --color-text-secondary link — explicitly NOT verdigris. Inviolable #2 use #8 (Plan CTA) is reserved for the trial-expiry modal specifically, per Component Spec. Routine "approaching limit" prompts use the neutral CTA token. Card is shown when usage exceeds 60%; hidden below that. The "read-only in V1" italic note appears while Stripe wiring is deferred (V2). "View plans →" link target is settled in §05 below.
8
BYOK primary card — tokens only
Component Spec §17.6 · Product Spec v1.9 §3.1 BYOK Tiers · simplified 2026-05-17
Header row: plan name + provider-key status (last_four + last_validated relative time, same pattern as OrgAnthropicKeyPanel). Body: a three-row token table with In / Out / Total tokens. Total row separates with a 1px top border. No dollar amount surfaced — same provider-neutral rationale as annotation 3. No allocation gate applies — isByok() bypasses checkTokenBudget entirely (V1.x-B.1.2 invariant). Closing caption clarifies the billing model: provider handles billing, Stelavox does not charge for usage on BYOK, refer to provider for current pricing.
9
Compact empty states — variants E + F
User direction 2026-05-17 — empty states drawn explicitly
A brand-new org (just signed up, or just after period rollover via M-141) starts at 0% / 0 tokens. The compact form shows 0% · renews in 30d (Non-BYOK) or 0 in · 0 out (BYOK) — no alert dot, no special colour. Director state stays "idle". Identical layout to active states so the surface doesn't reshape between empty and active — only values change.
10
Full-form empty states — §02b + §03b
User direction 2026-05-17 — empty states drawn explicitly
Non-BYOK empty (§02b): same primary card layout; usage bar shows 0%; soft CTA hidden (60% threshold not crossed). BYOK empty (§03b): primary card replaces the token table with a centred italic line "No LLM activity yet this period." plus a one-line explanation in --text-m. Both routes work without errors when the org row is fresh; both surfaces transition seamlessly to populated state as soon as the first agent_job completes (realtime subscription fires).

Settled decisions (per user feedback 2026-05-17)
  • No 30-day sparkline. Dropped per user direction — basic usage is enough.
  • No past-periods card. Dropped per user direction — same reasoning.
  • No "Current Director session" indicator. Dropped per user direction — was ambiguous (BYOK only saw aggregate-this-period anyway).
  • No by-model breakdown (BYOK). Dropped — keeps the surface simple. V2 candidate if BYOK users want spend-attribution.
  • No by-project / recent-activity breakdown. Dropped — focuses the surface on the essential question: how much have I used and when does it reset.
  • Empty-state variants drawn explicitly. Per user direction — see §02b + §03b above. Cover fresh-period (Non-BYOK) and no-activity-yet (BYOK).
Open decision before build kicks off
"View plans →" link target in V1. The soft upgrade CTA at >60% usage shows a "View plans →" link. V1 has no Stripe / upgrade flow yet — so where should this link actually go when a user clicks it? Three options:
  1. (a) Link to /settings/plan — a separate read-only page that lists the four V1 plans (Trial / Writer / Author / Pro) with their pricing and allocations from platform_config. PlanPanel is on the V1.x-D list anyway as a separate wireframe; this would land alongside CostMeter. The link works on day one; V2 swaps the static panel for the live Stripe flow.
  2. (b) Link to a marketing URL (e.g. stelavox.com/pricing) — keeps the in-app surface lean but couples to a marketing site that doesn't exist yet in dev.
  3. (c) Drop the link entirely — the CTA becomes pure copy ("Approaching the limit? Upgrade in V2"). Honest about V1's state but loses the directional signal.

Recommendation: option (a). PlanPanel is already on the V1.x-D build list (a separate wireframe to follow); making the "View plans →" link wire into it costs nothing extra and gives V1 a coherent settings nav. V2 then replaces only the upgrade-flow CTA inside PlanPanel with the Stripe Checkout button.

Member-vs-admin visibility (just noting the rule)
Per the M-137 RPCs (V1.x-C.3) any organisation member can read usage status — no admin gate needed on this read-only surface. The route /settings/usage resolves the user's primary organisation server-side using the same precedence rule as the OrgAnthropicKeyPanel page (owner > admin > member; oldest joined_at tiebreak). Multi-org users see usage for whichever org appears first; explicit org selection is V2.
