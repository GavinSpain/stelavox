04 — Annotations
1
Mount + auth gate
Component Spec §17.5 · TA v2.7 · V1 admin scope
Routes at /admin. Admin-only. Open decision: in V1 the simplest auth path is an env-var allowlist (PLATFORM_ADMIN_EMAILS) checked server-side. V2 candidates: a users.is_platform_admin column, or app_metadata.role='platform_admin' on the auth row. The route reads ALL orgs (bypasses standard RLS via service-role client + an explicit allowlist check); page-server-component checks first and redirects on miss. Inter typography throughout; no verdigris on any dashboard surface — admin views are passive observation, not affirmative action.
2
Time-window selector
Component Spec §17.5 · TA v2.7 §3.6 metrics_minute_buckets
Four windows: Live (current snapshot) · 1h · 24h · 7d. Data sources differ per window: Live → realtime counts from agent_jobs / director_turns; 1h / 24h → metrics_minute_buckets aggregations; 7d → metrics_minute_buckets daily rollups (collapse minute granularity to hourly or daily depending on retention — the M-125 purge keeps minute buckets 90 days). Window changes update every section's data source; URL reflects via ?window=1h for shareable links.
3
Live counter quartet
Component Spec §17.5 §1 (live registry) · agent_jobs + director_turns + briefs
Four atomic counts: active Director turns (director_turns WHERE status='in_progress'), running agent_jobs (agent_jobs WHERE status='running'), queued (agent_jobs WHERE queue_status='queued'), failures last 24h (agent_jobs WHERE status='failed' AND created_at > NOW()-24h). The failures counter colour-shifts to --st-rev when >10 and --destr when >30 (illustrative thresholds; tune in V1.x-E follow-up). Sub-line beneath each number gives context (delta, breakdown, attribution).
4
Queue depth by class
Component Spec §17.5 §2 · TA v2.7 §3.6 agent_jobs.traffic_class + wfq_state
Per-class queue depth from agent_jobs WHERE queue_status='queued' GROUP BY traffic_class. Bar widths are relative to the cap that triggers WFQ back-pressure (Class 3 in the wireframe is hitting 84% — bar colour shifts to --st-rev attention-amber). Class 1 (interactive Director) typically lowest; Class 4 (scheduled/parked) lowest priority. The four classes match the V1.x-B.2.2 throttle model.
5
Anthropic headroom
Component Spec §17.5 §3 · NEW DATA SOURCE needed
RPM / ITPM / OTPM / concurrent-connection utilisation pulled from Anthropic's rate-limit response headers (anthropic-ratelimit-*). Open decision: capturing these requires a new anthropic_rate_limit_samples table populated by the agent runner on every response. V1.x-E MVP scope question — ship the capture mechanism now, OR defer and surface only the wfq_state + bucket signals which are already captured? Recommendation: ship a tiny capture in V1.x-E (M-143) — it's a small ALTER PUBLICATION-style addition and unblocks the most-important capacity signal.
6
Dispatch rate sparkline
Component Spec §17.5 §2 · TA v2.7 §3.6 metrics_minute_buckets.dispatch_rate
30-bar sparkline (~2-min buckets over the last hour for the 1h window). Reads metrics_minute_buckets WHERE bucket_started_at > NOW()-60m. Peak bar colour-shifts to --ag-run for callout. Axis labels show "60m ago" / "peak X jobs/min · Nm ago" / "now". Click on a bar drills down to the per-minute detail (V1.x-E polish or V2).
7
Failures by class — A through E
Component Spec §17.5 §4 · Director Arch v2.4 §10 five-class taxonomy · failure_taxonomy_samples
Reads failure_taxonomy_samples grouped by failure_class. Each class shows count + human label + colour-coded pill (A blue/info, B amber, C amber, D destructive, E destructive-saturated). Auto-recovery rate beneath: SUM(auto_recovered) / SUM(failed_total) from the same window — surfaces in green when > 70%, amber 50-70%, destructive < 50%. The "0 in E (hard system)" line is the most-important signal for V1 launch: any non-zero count there is a paging-level incident.
8
Top organisations by usage
Component Spec §17.5 §5 · organisations.token_usage_credits + token_allocation_credits
Top 5 by recent-window credit consumption. Sub-line shows plan + active-Brief count for context. Per-row "%" is the org's token_usage_credits / token_allocation_credits for non-BYOK; for BYOK shows raw tokens with a "—" placeholder for percentage (no Stelavox cap applies; BYOK billing is between user + provider per provider-neutral rule). Click drills into per-org spend timeline (V1.x-E polish).
9
By-model spend distribution
Component Spec §17.5 §5 · agent_jobs.cost_credits grouped by model_id
Per-model platform credit totals for the window. Bars are relative to the largest. Beneath: total credit spend + corresponding dollar estimate (computed from anthropic_pricing for internal cost tracking — admin sees real dollars, end-users don't per V1.x-C provider-neutral rule). BYOK jobs counted in the totals at credit zero — they don't consume platform allocation, so they appear in token counts only on the per-org list (annotation 8) not here.
10
Capacity alerts
Component Spec §17.5 §6 · sustained-utilisation threshold
Generated when a metric crosses a configured threshold sustained for N minutes (e.g. ITPM >75% for 10 min). Thresholds live in platform_config alongside the other operational keys (admin.alerts.itpm_warn_pct, admin.alerts.itpm_sustained_minutes). When no alerts active, the card shows "No capacity alerts" with a green-toned status line. When triggered: each alert shows title + summary + recommended action + drill-down link. Alerts are informational only — no automated remediation in V1.
11
Synthetic probes
Component Spec §17.5 §7 · NEW DATA + cron needed
A small fleet of canned operations run on a cron schedule against a dedicated probe org (separate from any real user data). Each probe = a specific Director turn / workflow / agent op that exercises the full pipeline. Each run records pass / fail + duration + token usage in a new synthetic_probe_runs table. Dashboard surfaces last cycle's results + a stale indicator if it's been >15 min since the last run. Open decision: probe set scope. Recommendation for V1.x-E: ship 3 probes (Director-small + Workflow-expand + Refine-accept-round-trip). BYOK probe deferred (requires test key).
12
Non-admin gate
Brand voice — direct, no alarm
Server-rendered redirect path: if the authenticated user's email isn't in PLATFORM_ADMIN_EMAILS, the page renders the gate (no 403, no error stack). Brand voice: explain + offer a back-link. No verdigris. The gate page itself is publicly reachable as an empty shell; the data-loading layer below is the real gate. Belt-and-braces: the API endpoints (/api/admin/*) check the allowlist server-side too, so a non-admin can't hit them via API directly.
13
High-alert state
Component Spec §17.5 §6 + §3 (Anthropic headroom)
When > 1 alert is active, the header sub-line escalates to --st-rev attention-amber with a "⚠ N active capacity alerts" summary. The alert-banner stack at the top of the page lists each alert in severity order. Counter values colour-shift: counters in the warn band use --st-rev; counters past the destructive threshold use --destr. The whole page stays passive observation — no operator action button in V1 (operators take action via Supabase / Vercel admin consoles externally).

Open decisions before build
  1. Admin auth mechanism. Three options: (a) PLATFORM_ADMIN_EMAILS env-var allowlist — simplest, no schema change, suitable for V1 with 1-3 admins; (b) users.is_platform_admin BOOLEAN column — needs admin UI to manage; (c) app_metadata.role='platform_admin' on auth.users — Supabase-idiomatic but requires service-role writes. Recommendation: option (a) for V1.x-E; revisit at V2 when a real admin user base exists.
  2. Anthropic rate-limit capture. Ship in V1.x-E or defer. The headroom widget is the most-important capacity signal; without it we only see internal queue state, not provider-imposed limits. Recommendation: ship — add anthropic_rate_limit_samples table + agent-runner hook that reads response.headers and inserts a row asynchronously. Small footprint; high admin-value.
  3. Synthetic probe scope. Three probes (Director-small + Workflow-expand + Refine-accept) or more? Recommendation: three for V1.x-E ship; add Edge Function / BYOK probes in V1.x-E polish or V2 once probe org has a real BYOK key available.
  4. Capacity alert engine. Sustained-utilisation alerts need a small evaluator. Options: (a) compute on dashboard load (cheap, no extra infra; alert "active" computed each request); (b) pg_cron evaluator writes to an admin_alerts table. Recommendation: (a) for V1.x-E — admin opens dashboard occasionally; evaluating thresholds at load time is fine. Push-model alerting (Slack / email) is V2.
  5. Drill-down navigation. Wireframe shows "View top consumers →" inline link. Open: per-org / per-model / per-class drill-downs as separate pages or modal overlays? Recommendation: in-page expanded sections for V1.x-E (cheaper than building separate routes); drill-downs to per-document operations remain user-side (existing SchedulerPanel handles that already).
